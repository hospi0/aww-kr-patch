# 텍스트 주소지정 구조 — 길이 성장 가능 여부

작성 2026-07-20 / 세션 1 후반. 판정 대상 = 초기조사 §6 질문 1.

## 결론

**텍스트 레코드를 가리키는 오프셋 포인터 테이블은 없다.**
레코드는 **풀 선두부터 `0xFFFF`를 세어 나가는 서수(ordinal) 인덱스**로 지정된다.

→ **레코드 길이는 자유롭게 바꿀 수 있다.** 단 아래 불변식을 지켜야 한다.

## 근거

### 1. 오프셋 포인터 부재 (3개 모듈)

`/GMSELDT`, `/SAKUSEN`, `/GMDT`의 텍스트 풀에서 전 레코드 시작 오프셋 집합 S를 만들고,
파일 전체를 u32/u16 × (절대 / 풀기준 바이트오프셋 / 풀기준 워드오프셋)로 훑었다.

| 해석 | GMSELDT | SAKUSEN | GMDT |
|---|---|---|---|
| u32 절대 | 28 | **0** | **0** |
| u16 절대 | 246 | **0** | **0** |
| u16 워드오프셋 | 950 | 2986 | 750 |
| (레코드 수) | 102 | 699 | 96 |

⚠️ **u16 히트 수를 근거로 쓰면 안 된다** — 레코드 수의 4~9배가 나오는 건
작은 u16 값이 대용량 파일에서 우연히 맞는 노이즈다(기대 노이즈량 문제).
의미 있는 신호는 **u32 절대 포인터가 사실상 0건**이라는 것.

`tools/findptr.py`로 **연속·순증가·중복없음** 조건(6개 이상 뭉침)을 걸어
진짜 테이블 형태를 찾았을 때도 **전 모듈 0건**이었다.

### 2. 서수 인덱스 목록의 실물

`/GMSELDT` 0x5f0~0x70e에 **1바이트 레코드 번호 목록**이 있다.

```
01 02 03 … 24 | fe | 25 26 … 3e | fe | 3f … | fe | … | b0 | ff
```

- 값 = 레코드 서수 (0x01 … 0xb0)
- `0xfe` = 그룹 구분 (화면/메뉴 단위로 보임, 8개)
- `0xff` = 목록 끝

**바이트 크기 인덱스**이므로 한 풀의 레코드는 최대 253개다.

### 3. 모듈 파일 레이아웃 (GMSELDT 기준)

| 범위 | 내용 |
|---|---|
| 0x0000 | 폰트 파일명 ASCIIZ (`ASCGSCG`) |
| 0x0040–0x0130 | 리소스 디렉터리. 16 B 레코드 × 15: `u32 id / u32 ? / u16 w / u16 h / u32 (0x0020<<16 \| 파일오프셋)` |
| 0x0130–0x05f0 | 자산명 ASCII(`ITMSN`,`CGWM01`…), 기타 테이블 |
| 0x05f0–0x070e | **서수 인덱스 목록** (위 §2) |
| 0x0710–0x13dc | **텍스트 풀** (0xFFFF 구분 레코드 101개) |
| 0x13dc– | 스프라이트 (디렉터리가 가리킴) |

`/SAKUSEN`·`/MUSEUM`·`/INTERM`은 선두가 SH-2 코드(`2f e6 …`)라 이 헤더가 없다.
`/GMDT`는 순수 데이터. **모듈 종류가 3가지이므로 한 레이아웃을 일반화하면 안 된다.**

## 재삽입 불변식

1. **레코드 개수와 순서를 정확히 보존한다.** 서수로 참조되므로 하나만 밀려도 전부 어긋난다.
2. **빈 레코드도 레코드다.** `0xFFFF`가 연달아 나오는 자리(길이 0)를 지우면 안 된다.
3. 풀이 커지면 뒤 데이터가 밀린다 → **헤더 리소스 디렉터리의 `0x0020xxxx` 오프셋을 갱신**해야 한다.
   `/GMSELDT`류는 헤더에 다 있어 갱신 가능. **코드 모듈(`/SAKUSEN` 등)은 SH-2 코드 안에
   상수 오프셋이 박혀 있을 수 있어 아직 미검증.**
4. ⏳ **파일이 적재되는 RAM 슬롯 상한은 아직 모른다.** 삼국지11 entry4처럼
   "디스크는 되는데 RAM에서 죽는" 경우가 있으므로, 성장분을 실기로 확인하기 전에는
   **원본 크기 유지(length-locked)를 기본값**으로 둔다.

## 부수 발견 — 원본 데이터 오타

`/GMSELDT`의 저장 메뉴는 실제로 **「セープ」**로 저장돼 있다(정상은 セーブ).
같은 파일의 「武装タイブ」(정상 タイプ)도 마찬가지. 두 낱말 모두 탁점/반탁점이 뒤집혔다.

폰트 5종 + `SCHOOL`·`MAPSCT` 내장분까지 **글리프 순서는 전부 동일**하고,
같은 파일의 `キャンペーン`(207) `ベルギー`(212) `ポーランド`(208) `パリ`(204) `ボタン`(213)이
모두 정상 표를 지지하므로 → 폰트 문제가 아니라 **원본 제작 시 오타**로 판정.

★ 이 판정 과정이 매핑표 확정의 결정적 근거였다.
16×16 AA에서는 탁점(゛)/반탁점(゜)을 육안으로도 픽셀 구멍 검출로도 못 가른다.
**문맥 낱말(고유명사·외래어)로만 확정된다.**
