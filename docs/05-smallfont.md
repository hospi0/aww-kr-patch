# 05. 소형 8x8 폰트와 이름 테이블 (세션4)

세션3-b가 "무기명은 ASC16CG·SJIS 어디에도 0곳"으로 남긴 숙제의 답.
무기명(`7.92㎜MG` `ブソウナシ`)·HUD 수치는 **제3의 폰트/인코딩**을 쓴다.

## 포맷

| | |
|---|---|
| 글리프 | **8x8, 4bpp, 32 B/글리프**, 헤더 없음 |
| 니블 순서 | **상위 니블 = 왼쪽** ← 16x16 폰트(ASC16CG 등)와 **반대** |
| 색 | 2색 하드엣지 (0 = 투명, 15 = 잉크). AA 없음 |
| 텍스트 | **1바이트 = 1글리프** (16x16 계열의 BE16 인덱스가 아니다) |

여태 못 찾은 유일한 이유가 니블 순서다. 기존 규약으로 읽으면 글자가 조각나 보여 폰트로 인식되지 않는다.

## 코드표 (`tools/smallfont.py`)

```
0        공백
1~10     0-9
11~36    A-Z
37~62    a-z
63~109   ア イ ウ … ワ ヲ ン ヴ
110~124  ガギグゲゴ ザジズゼゾ ダヂヅデド
125~129  バビブベボ      ★ASC16CG와 반대 순서
130~134  パピプペポ
135~143  ァィゥェォッャュョ
144~171  . · ’ = / ㎜ ㎏ ? ! % ー : Ⅰ~Ⅵ [ ] ✕ ★ ( ) +
176~     유닛 아이콘 등 그래픽 (글자 아님)
```

- **149 `㎜` · 150 `㎏` 는 합자 글리프 한 칸.** `'kg'`처럼 두 글자로 쓰면 인코더가 두 칸으로 뱉는다.
- 탁점/반탁점 순서는 「ブソウナシ」(武装ナシ)를 127로 인코딩했을 때만 4개 모듈에서 히트한 것으로 확정.

## 발견 방법 (재사용 가능)

세이브스테이트 VRAM에서 **「2색만 쓰는 8x8 타일이 길게 연속하는 구간」**을 찾는다.
16x16 폰트는 4bpp 안티에일리어싱이라 회색 계조가 섞이고, 소형 폰트는 하드엣지 2색이므로
이 한 가지 기준으로 깨끗이 갈린다 — VDP2 VRAM 0x000000에서 **143타일 구간 하나만** 떴다.

⚠️ 잉크율·빈행율·고유율을 조합한 일반 폰트 검출기는 **전 모듈에 만점**을 줘서 쓸모없었다.
검출기를 정교하게 만드는 쪽이 아니라 **대상만 갖는 물리적 성질**을 찾는 쪽이 답이었다.

도구: `tools/statedump.py` (스테이트 섹션 추출) · `tools/staterender.py` (타일 렌더)

### 공급 (재정의 가능 슬롯) — 실측
- 소형폰트 가나 사용 = **80 / 81칸** (모든 알려진 소비자 합집합: 무기·지형·지명·유닛·UI풀)
- 안 쓰는 소문자 5칸(h p q x y) + 안 쓰는 기호 7칸(’ = ? ! % ★ +) = **12칸**
- 전부 번역/로마자화 시 = 가나 80 + 비가나 12 = **92칸**, +240확장 11 = **103칸**

★★**부분 한글화는 구조적으로 불가.** 폰트 5벌이 바이트 동일 → 가나 글리프 X를 한글로 재정의하면
  X를 쓰는 **모든** 소형폰트 텍스트가 바뀐다. 어떤 카테고리를 가나로 남기면 그 가나가 공급을
  잠근다(시나리오 실측: 무기+지형만 한글·UI 가나유지 시 공급이 92→50으로 급락, 수요 91에 41 부족).
  ⇒ **전부 한글/로마자화가 유일한 길**이고, "원문(가타카나) 유지"는 슬롯 회수에 도움이 안 된다.

## 8x8 한글 렌더 (`tools/hangul8comp.py`)

TTF 축소는 8px에서 전멸한다(맑은고딕·굴림체·돋움체·바탕 8~12px 전부 시도, `work/hangul8_compare.png`).
획을 직접 그리는 조합형으로 간다. 실측한 규칙:

- **가로는 7픽셀만** 쓴다 (col7 = 자간). 8픽셀 다 쓰면 옆 음절과 획이 붙는다.
- **받침은 3줄** 준다. 2줄이면 ㅇ/ㅁ/ㅊ이 뭉개져 「총」이 「즈」로 읽힌다.
- **받침은 5폭**. 바로 위 모음 가로획(7폭)과 폭이 같으면 한 덩어리로 보인다.
- **ㄹ 받침과 대각선 자모(ㅅㅈㅊㅎ)는 리터럴 비트맵**으로 고정. 눌린 박스에서 파라메트릭 래스터가
  무너진다(ㄹ이 3줄 통짜 블록이 된다).
- **ㅇ은 모서리 뺀 사각**으로만 ㅁ과 갈린다.

## 폰트 재배치·확장 (실기 확정)

지배하는 상수는 **3개**뿐이다. 파일 끝의 `(주소, 크기)` 디스크립터는 **업로드량과 무관**하다(실기 확인).

| 상수 | MUSEUM 위치 | 값 | 역할 |
|---|---|---|---|
| 폰트 RAM 주소 | `0x2460`, `0x12688` | `0x060709e8` | 어디서 읽을지. **여러 곳이므로 전수 검색 필수** |
| 업로드 롱워드 개수 | **`0x23FC` (u16)** | `0x0728` = 1832 = 7328/4 | 몇 글리프 올릴지 |

### ✅ 5개 모듈 전수 확정 (세션5, `tools/find_smallfont_consts.py` 로 SH-2 역추적·검산)

MUSEUM 을 기준으로 로직을 검증한 뒤 자동 추출. 패턴이 완벽히 균일하다.
디스크립터 = `fo + 229*32`, 그 안의 (RAM주소, 0x1ca0) 검산 전부 통과.

| 모듈 | 폰트 fo | 크기 상수 (u16) | 폰트주소 리터럴 | VRAM 목적지 | 업로드 |
|---|---|---|---|---|---|
| MUSEUM | 0x109e8 | **0x23fc** | 0x2460, 0x12688(desc) | 0x25e01e00 | 1곳 ✅실기 |
| SAKUSEN | 0x1c9cc | **0x3584** | 0x35c0, 0x1e66c(desc) | 0x25e00000 | 1곳 |
| KEKKA | 0x17cb8 | **0x4ac · 0x8204** | 0x4c8, 0x8214, 0x19958(desc) | 0x25e01e00 ×2 | **2곳** |
| INTERM | 0x3ab40 | **0x6ab6 · 0x6eba** | 0x6b3c, 0x6f28, 0x3c7e0(desc) | 0x25e01e00 ×2 | **2곳** |
| GMDT | 0x28ef8 | **0x18930 · 0x6e3b4** (`GAME`) | 0x18984, 0x6e3f0(GAME), desc@GMDT 0x2ab98 | 0x25e00000 + 0x060f279c | **2곳** |

⚠️ **KEKKA·INTERM·GMDT 는 업로드 루틴이 2곳** — 확장 시 크기 상수 **둘 다** 0x0780 으로 바꿔야 한다.
⚠️ **VRAM 목적지가 모듈마다 다르다.** 실기 확정은 MUSEUM 의 `0x25e01e00` 뿐. KEKKA·INTERM 도 같은
   dst 라 신규 11칸(0x25e03aa0~) 안전 유력. **SAKUSEN(`0x25e00000`)·GMDT 는 신규 11칸이 얹히는
   VRAM 구간이 미검증** — 이 모듈들의 확장은 실기로 따로 확인해야 한다.
⚠️ GMDT 2번째 사이트 dst `0x060f279c` 는 VDP2 VRAM 이 아니라 Work RAM High(작업 사본).
   R4=폰트 src·R6=개수는 동일하므로 크기 상수는 함께 갱신 대상.

원문 참고(세션4 근사값, 위 검산값으로 대체): SAKUSEN `0x35c0`+`0x1e670` / KEKKA `0x4c8`·`0x8214`+`0x1995c` /
INTERM `0x6b3c`·`0x6f28`+`0x3c7e4` / GMDT `GAME` 0x18984·0x6e3f0.

### 크기 상수 찾는 법 — SH-2 리터럴 역추적

1. 폰트 RAM 주소가 들어있는 리터럴 위치를 찾는다 (예: `0x2460`).
2. 그 리터럴을 읽는 명령을 찾는다. `MOV.L @(disp,PC),Rn` = `0xDnDD`,
   target = `((A+4) & ~3) + disp*4`.  → `0x2392`에서 R4로 로드.
3. 그 근처의 인자 세팅을 읽는다. 여기선 직전 `0x238e`의
   `MOV.W @(disp,PC),R6` = `0x9nDD`, target = `(A+4) + disp*2` → `0x23FC`.
4. 호출 `0x2396 JSR @R2` 의 인자 = (R4=src, R5=VRAM dst, **R6=롱워드 개수**).

⭐이 기법은 ASC16CG의 900글리프 천장을 뚫을 때도 그대로 쓴다.

### 상한

VDP2 VRAM 타일 **229~243은 비어 있고 244부터는 다른 것이 쓴다**(세이브스테이트 실측).
→ 안전 확장은 **240글리프 = 신규 11칸**. 인덱스가 1바이트라 이론 상한은 256.

VDP2 VRAM 자체는 여유가 많다(512KB 중 빈 8KB 블록 35개, `0x1c000~0x40000` 144KB 연속 등).
폰트 목적지(리터럴 `0x2458` = `0x25e00000`)를 옮기면 256글리프를 다 쓸 여지가 있으나,
타일 인덱스 기준점이 함께 움직여 244+를 쓰는 다른 것과의 관계가 **미검증**이다.
